重要核对结果：

1. SDK 的 env 会合并 process.env；测试需要显式将继承键置 undefined，而不只是覆盖 HOME。
2. `ctx.executeTool()` 返回 `{ result, isError, ... }`，不是裸工具结果；fixture 驱动准确传递嵌套结果与错误标记。
3. custom message 的 busy steering 直接进入 agent 队列，**不产生包含正文的 `queue_update`**。测试改为观测立即转发的真实 sendMessage 调用、下一 turn 的消息/上下文，不用不存在的队列事件作为标准。
4. 手动压缩在历史太小时可能在 hook 前拒绝；临时 settings 的 `keepRecentTokens: 1` 使测试历史实际进入压缩 hook，hold 期间验证真实 prompt 拒绝。生产配置不受影响。

| 文件 | 职责 |
| --- | --- |
| `index.ts` | 稳定根入口，转导出 `src/index.ts`；package manifest 指向该入口 |
| `src/index.ts` | 每个扩展实例新建管理器；立即委托 pi.sendMessage；所有 session_shutdown reason 统一清理 |
| `src/tools.ts` | 注册唯一 `subagent` 工具；普通 object schema；execute 再校验、取得调用时父快照、返回确认 JSON/details |
| `src/config.ts` | 文本/枚举/模型对校验；独立继承 thinking 和 provider/model，不改变原始文本 |
| `src/rpc-client.ts` | 定位加载中 SDK 对应的绝对 CLI；官方 RpcClient；start + getState；原样 prompt；归一化缺失文本为 null；幂等有界 stop |
| `src/manager.ts` | 当前运行时的精确名称 Map、同步预留、spawn/send、失败回滚、settled 取文本、过期保护、幂等并行 shutdown |
| `src/report.ts` | 名字/最后 assistant 文本写入 content；固定 customType/display/steer/triggerTurn |
| `src/types.ts` | 最小配置快照、输入/确认/报告类型和可注入 RpcAdapterFactory |

公开工具：

```ts
subagent({ action: "spawn", name, message, provider?, model?, thinking? });
subagent({ action: "send", name, message, mode?: "steer" | "followUp" });
```

- name/message 非空且非纯空白，保留原文。名字在一个父运行时内唯一，启动中也预留；失败释放，完成不释放。
- provider/model 同时提供或省略；省略时从当次 ctx 继承模型对；thinking 独立继承或覆盖。缺失必要父配置直接错误。
- 成功文本为 `{"name":"…","disposition":"started|queued|handled"}`，details 同形。只等待接收确认，handled 不保证 settled。
- 初始 `prompt(message)`，后续 `prompt(message, undefined, mode)`；不改用 steer/followUp 独立 RPC 入口，不等待 promptAndWait。
- 参数/RPC/压缩错误按 Pi 工具失败返回；不等待压缩、不扩展层重试。
- 每次 settled 回报 `Subagent: <name>\n\n<最后 assistant 文本>`；null 显示 `(No assistant text available.)`。固定 `subagent.report`、`display: true`、`{ deliverAs: "steer", triggerTurn: true }`。
- `extension(pi, { createClient? })`、`createRpcAdapterFactory(createClient?)` 继续保留已有最小测试注入边界；没有另造管理框架。

## 真实离线 CLI 集成方式

每个集成场景创建临时 root，包含独立 workspace、HOME、agent/extensions、settings、config/cache/session 路径及文件 gates：

1. 使用官方 RpcClient 启动实际 Pi CLI 父进程，`--no-session --thinking low`，选择临时 provider `fixture/fixed`。
2. 清除继承的环境键（包括认证、PI_SESSION_*、NODE_OPTIONS 等），只保留 PATH/locale/系统必需项，配置 PI_OFFLINE、禁版本查询和 telemetry。
3. 经**默认全局扩展发现**加载两个临时扩展：
   - wrapper 导入绝对生产根入口并执行 factory；只记录加载和立即转发的 sendMessage（准确记录 options），不替换管理器、RPC 创建或调度。
   - fixture 注册本地固定响应 provider 和测试驱动工具，不发模型 HTTP；fetch 误调用会记录并抛错。
4. 固定 provider 产生真实 assistant tool-call，测试驱动工具通过 SDK 的 `ctx.executeTool("subagent", …)` 进入生产工具。生产适配器以**默认构造器**创建官方 RpcClient 与子 CLI，无额外生产参数/env 注入。
5. 子 CLI 继承隔离环境，经同样默认发现实际加载生产扩展和固定 provider。生产 `--exclude-tools subagent` 仍保留其他资源。
6. 固定响应的文件 gate 控制工作完成时机；事件/日志/最终模型上下文证明实际行为，不靠任意 sleep 猜测队列调度。短轮询仅用于跨进程观测，精确 Promise 竞态仍由既有 fake tests 覆盖。
7. 清理停止父进程、验证日志中所有 PID 均消失、确认无 fetch 尝试并删除临时 root。失败路径提供 SIGKILL 紧急清理；正常验收在紧急分支前即确认 PID 消失。

**没有使用 `--no-extensions`、未加载生产扩展、只检查启动参数或仅手工 emit settled 来证明端到端排除/调度。** 生产加载日志、注册表、模型工具声明、可调用集合、尝试重激活、两个 action 的实际嵌套错误及子进程创建数均有断言。父驱动实际成功执行同一生产工具是正向对照。

### 两个新增集成测试的实际覆盖

第一场景（父与三个子进程，再替换运行时重用名字）：

- spawn 返回 started 时 child 被 gate 持有，尚无报告；随后子工作、settled、最后文本查询、真实父 custom message 完整贯通。
- alpha 运行中 send 两次：默认 steer 与显式 followUp 均返回 queued；真实 input hook 接收对应 mode；三次真实 provider 请求的上下文顺序准确为 initial → initial+steer → initial+steer+followUp，最终只有一份 alpha 报告。
- beta 与 alpha 同时持有不同 gate、PID 均存活，先完成 beta 只归属 beta；同名 alpha spawn 返回错误且不创建额外进程。
- 子代理报告后同一 PID 继续 send，返回 started，再次回报保留原上下文，未重建进程。
- 真实 CLI 状态/请求验证模型对与 thinking 继承；beta 单独 thinking high；gamma 覆盖 `fixture-other/alternate`，独立继承父后来设置的 medium。其他配置组合和父快照变更由既有参数矩阵覆盖。
- handled 输入不启动子运行；实际手动压缩 hold 期间的 send 返回 Pi 的 compaction 错误，无伪造拒绝；后续真实请求中没有被拒绝文本。精确“仅调用一次、不重试”另有适配器/工具替身断言。
- 子模型发起 fixture_probe；重激活 subagent 无效，嵌套 spawn/send 均真实返回 `Tool subagent not found`，注册表/声明/可调用集合无 subagent，也没有第四个子进程。
- 空闲父收到报告后真实以 messageType custom 运行，provider 上下文含名字和结果；忙时 gamma 报告以固定 steer/triggerTurn 投递，在当前响应 gate 放开后的下一 turn 消费，而非等待新用户输入。
- 通过真实 `new_session` 发出 shutdown new，同时停止空闲与工作中的子进程、确认全部 PID 消失；释放旧 gate 后无迟到报告；旧名字 send 报未知、新运行时能重新 spawn 同名。

第二场景：子 CLI 已执行生产 factory，但在 fixture async factory 中暂停，尚未握手/提交任务。父官方 stop 触发真实 shutdown quit，停止这个仍在启动的子 PID；关闭不等待 30 秒 getState 请求期限，随后没有任务/settled。测试也确认父 shutdown handler 完成。
