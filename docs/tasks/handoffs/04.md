## 实际接口及任务 05 用法

```ts
import { SubagentManager } from "./manager.ts";

// 在扩展实例内创建，不启动进程；每个父运行时一个独立实例。
const manager = new SubagentManager({
  sendMessage: (message, options) => pi.sendMessage(message, options),
  // createClient 可省略，默认 createRpcAdapter。
});

await manager.spawn(spawnInput, parentConfigSnapshot);
await manager.send(sendInput);
await manager.shutdown();
```

**接口调整**：任务 03 的临时 `onEvent(child, event)` 构造选项及导出的 `SubagentEventListener` / `SubagentHandle` 已撤掉。管理器现在自行消费 settled，不再把生命周期判断交给外部消费者。必需选项改为 `sendMessage: ParentMessageSender`；没有默认静默丢弃回报的 no-op。仓库内原调用点/测试已迁移。

`src/report.ts`：

- `ParentMessageSender` 的两个参数从 `ExtensionAPI["sendMessage"]` 派生，返回值允许 `void | Promise<void>`；与当前同步 void 的 Pi API 兼容，也能测试同步抛错与异步拒绝。
- `createReportReceiver(sendMessage): ReportReceiver` 把现有 `{ name, text }` 边界转换成 Pi 消息。
- 固定消息：`customType: "subagent.report"`、`display: true`。
- 固定选项：`{ deliverAs: "steer", triggerTurn: true }`；不受 send.mode 影响。
- content 为 `Subagent: <原始名字>\n\n<最后 assistant 文本>`；文本原样保留，不截断、不拼历史、不取 thinking/工具结果。
- null 时使用 `(No assistant text available.)`；空字符串不是 null，不替换为缺失提示。
- 名字和结果均写入 content，没有只放 details。

任务 05 应使用上面的立即委托包装绑定 `pi.sendMessage`，不要在注入函数内部另设延迟队列或在旧实例关闭后自行重投。session_shutdown 接线只需 await shutdown，不按 reason 过滤。每个替换运行时创建新实例，不重开旧实例。

## 回报语义和错误处理

1. 监听安装仍早于初始 prompt；starting 阶段的快速 settled 也有效，不要求 spawn 已返回。
2. 一个有效 settled 立即发起一次 `getLastAssistantText()`，取得结果后再检查关闭标志和记录对象身份，通过才投递。
3. 不计数 spawn/send，不订阅 agent_end 取文本，不调用 getMessages/promptAndWait，不等待 handled 后的虚构 settled。
4. 各 settled 的取文本独立启动，不为前一回报延迟下一次读取；若注入的异步请求反序完成，回报也可反序完成。没有额外排序或重读。
5. `reportSettled` 的完整读取、有效性判断、格式构造和父投递都位于 try/catch 内。同步 listener 只启动这个内部已捕错的异步函数，返回 void。
6. 读取或投递失败为 best effort 丢弃当前回报：不产生 unhandled rejection、不自动重试、不报告崩溃、不删除/停止子代理。下次 settled 仍可正常回报。
7. shutdown/回滚期间已开始的文本读取可以迟到 resolve/reject，但不会投递给旧父运行时；旧 listener 即使被 SDK 快照保留或名字重用，也不能触发旧回报。
8. 已经在 shutdown **之前调用**的父投递不可撤销；shutdown 不等待它完成，其迟到 rejection 仍被捕获。当前真实 Pi sendMessage 是同步 void 边界。

## shutdown 与清理契约

`shutdown(): Promise<void>` 是终止式、幂等的接口，无参数、无重开/恢复功能：

- 调用时同步置 closed，立刻拒绝新 spawn/send，阻止新读取与投递；即使尚未执行清理微任务也已生效。
- 并发和重复调用返回**同一个 Promise**。
- 并行处理所有 ready/starting/failed 记录，取消订阅并调用 stop，最终清空 Map（同时释放所有名字预留）。
- 每条记录的清理 Promise 由启动失败回滚和 shutdown 共享，避免重复 unsubscribe/stop；清理置 failed 后，迟到的 start/prompt 成功不会复活记录。
- 清理不 await 尚未完成的 start/getState、初始 prompt、send、文本读取或父投递。
- start 后、订阅后、初始 prompt 后均检查运行时有效性；同步 factory/onEvent/prompt 内重入 shutdown 也有保护。
- 一次微任务延迟让同步 factory/onEvent 完成资源赋值，再取得资源清理；名字在 factory 前就已预留。
- 取消订阅抛错仍尝试 stop；一个 stop 同步抛错或异步拒绝，不阻止其他子代理清理及记录清空。清理错误不盖过原始启动/提交错误，shutdown 本身采用 best effort 完成，不另发通知。
- 关闭时已在途的 spawn/send 若随后收到成功确认，会拒绝 closed 而非返回成功；原 RPC 拒绝仍保留其错误。

### 有界停止的实际依赖与限制

沿用任务 02 的生产适配器契约，而非新增一个只能结束等待、不能杀进程的外层超时：

- 生产适配器只等官方 start 的约 100ms 启动检查，不等 getState 请求。
- 官方 Pi 1.5.0 stop 发送 SIGTERM，最多等待 1000ms 后发送 SIGKILL；适配器合并重复 stop。
- 管理器并行调用这些有界 stop，所以不会累计成 N 个串行的停止期限，也不会等 SDK 的 30 秒请求期限。
- 注入的 RpcAdapter 也应遵守有界 stop 契约；不承诺任意永不完成的自定义 stop 能完成 shutdown。
- stop 真的抛出操作系统/终止错误时，管理器仍释放记录并隔离失败，但不能凭空保证对应进程已被 OS 杀死；没有额外重试或恢复。SDK 的 SIGKILL 兜底发出后也不等待 OS exit 回调；真实进程测试另确认进程最终消失。仍无进程树终止保证。

覆盖：

- agent_end/流式 thinking/工具结果不取文本、不回报；settled 才取 SDK 最后文本。
- 完整 customType/content/name/text/display/deliverAs/triggerTurn 断言。
- null/空字符串、连续运行、多条 send 合并到一个 settled、handled 无 settled。
- 初始 prompt 确认前的快速 settled；重叠 settled 各读一次；aborted settled。
- 文本读取和父投递的同步 throw/异步 reject 均被捕获，无重试、异常退出回报或进程移除；后续发送和回报仍正常。
- 文本读取中 shutdown、读取中初始 prompt 回滚并重用名字，均丢弃迟到结果。
- 已开始父投递在 shutdown 后拒绝，仍无 unhandled rejection，且不阻塞关闭。

- start/初始 prompt 的迟到成功与迟到拒绝；factory/订阅/prompt 同步重入关闭。
- rollback 与 shutdown 共享清理；取消订阅/stop 失败不阻塞其他子代理；关闭后 spawn/send 拒绝及重复关闭 Promise 身份稳定。
