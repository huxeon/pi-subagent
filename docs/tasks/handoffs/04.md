## 控制桥 API

父侧继续使用任务 03 的 `SocketClient`，方法名和 JSON 业务数据如下（不包含 name：连接地址已经定位到该子代理）。

```typescript
const client = await SocketClient.connect(runDir);
await client.request("message", { prompt: "原样输入", followUp: false });
// => { invoked: true }
await client.request("inspect", {});
// => { state: "working" | "idle" }，wait 默认 false
await client.request("inspect", { wait: true }, {
  timeoutMs: 1_800_000,
  signal,
});
// => { state: "idle", reply: { text, stopReason, errorMessage? } | null }
```

- `message.prompt` 必须为非空白字符串，原样传给 Pi，不 trim/翻译；`followUp` 可选 boolean，默认 false。
- idle 时直接调用 `pi.sendUserMessage(prompt)`（不传 delivery）；working 时 false/缺省使用 `{ deliverAs: "steer" }`，true 使用 `{ deliverAs: "followUp" }`。
- `{ invoked: true }` **仅表示公共 void API 调用已发起**。不是接受、排队、落盘、任务成功或完成证明。桥不等待 Pi 异步接受，不捕获内部异步错误当投递回执，不重投。message 后短暂仍 idle 的窗口照 spec 保留。
- `inspect.wait` 可选 boolean，默认 false。非等待响应不含 reply，也不访问 getBranch。
- wait=true 且 idle 立即读取当前分支返回；working 时延迟原 socket 请求，不订阅、不反向通知。
- 业务 params 要求 JSON 对象；未知方法为 `METHOD_NOT_FOUND`，非法参数为 `INVALID_PARAMS`。额外字段不参与处理。桥关闭时直接请求为 `BRIDGE_CLOSED`，已取消 signal 为 `ABORTED`；其他 handler/序列化错误沿用传输层。
- **timeout 不属于桥 params**：继续由客户端 `RequestOptions.timeoutMs` 执行 deadline 并发 cancel。任务 06 将工具秒数转为毫秒，wait 默认 1800 秒；不要忘记覆盖传输层默认的 30 秒。没有新增服务端 timer。
- 回复文本不做工具展示截断、不写回复副本。传输层继续保留 1 MiB 帧限制，超大结果返回 `RESPONSE_ERROR`，不会无限缓冲或静默截断。工具展示/截断留任务 06。

### 导出的接口

`src/child-bridge.ts`：

- `ChildPiAdapter`：仅 `isIdle()`、`getBranch(): SessionEntry[]`、公共 `sendUserMessage`；刻意不提供 abort/队列修改/资源发现能力。
- `AssistantReply`、`InspectResult`、`MessageResult`：上述结果形状的 TS 类型。
- `latestAssistantReply(entries)`：逆序找当前分支最近 assistant，提取所有 text blocks（换行连接），保留 `stopReason` 和存在的 `errorMessage`，没有 assistant 时 null。
- `ChildBridge(adapter)`：`handle` 是任务 03 的 `RequestHandler`；`agentStart()`、`agentSettled()` 接事件；`close(): void` 幂等；`waitingCount` 仅为内存诊断计数。
- `registerChildBridge(pi, runDir, options?)`：注册 session_start、agent_start、agent_settled、session_shutdown。`TransportOptions` 直接透传既有 listen（主要用于测试地址注入）。生产从相同扩展入口调用一次，不另外显式加载桥模块。

## 状态、分支与等待

1. 仅内存 working/idle。构造和每个请求用公共 `ctx.isIdle()` 初始化/刷新；agent_start 标 working，agent_settled 再确认 isIdle 才完成既有等待。没有 agent_end 注册，不把一次底层 run 结束当完成。状态查询即使看到 idle，也不会代替 settled 去完成已经登记的 working 等待。
2. 每个 working inspect 拥有独立等待记录及自身 AbortSignal 监听器；不使用连接内 id 做全局索引，不会因不同连接编号相同串扰。
3. 正常完成先删除记录、解绑监听器，再读取当前分支并 resolve；读取错误会 reject，不把它伪装成成功。
4. getBranch 在**响应时**调用，不缓存旧分支回复，不调用 getEntries 或 getLastAssistantText。空 error/aborted 回复不会被跳过，也不会退回较旧的成功回复；idle 不等于任务成功。
5. 白名单输出仅 text/stopReason/errorMessage，不返回 thinking、thinking signature、tool-call arguments 或其他原始内容块。错误和中止由回复结果信息表达，而不是第三种工作状态。
6. cancel/timeout/断线通过传输层对应请求 signal 同步删除其等待记录、解绑监听器并 reject handler Promise。传输层已删除 pending，消费该拒绝但不为取消请求发响应。之后 settled 不读取或生成该请求的结果。其他等待不受影响；没有 Pi abort、队列清空或状态修改。

## 生命周期与清理

- 环境变量**存在**即子角色；空值、相对路径、NUL 等非法路径用既有 `normalizeAbsolutePath` 拒绝，不退化成父角色；绝对路径做同一词法规范化，不 realpath、不筛选资源。
- 工厂只判角色及注册事件，不 listen、不启动 timer/长期资源。session_start 才创建适配器/桥并 `SocketServer.listen`；重复 start 不重复监听。
- session_shutdown 对 quit/reload/new/resume/fork 一律关闭该子侧控制桥和 socket（不负责停止其他 Pi）。先幂等拒绝/清理所有桥等待，等待可能尚在建立的监听完成后关闭自己的 server，断开客户端；关闭不会当作工作成功。
- shutdown 重入共享同一个清理 Promise，不等待 agent_settled。测试覆盖 start 尚未完成时的 shutdown。
- listen 失败由 Pi 扩展错误处理路径报告；shutdown 可再次安全执行，不 unlink/关闭他人的端点。测试覆盖第二个 runtime 碰到 `SOCKET_IN_USE` 后，原服务仍正常可用。
- socket 文件仍由既有 SocketServer/Node 清理；不手工重复 unlink，不删除 runtimeDir/runDir/session.jsonl，不写状态或等待请求。重载/切换由 Pi 创建新 runtime 后重新注册、重新监听；无进程级永久 sentinel。
- 保持正常资源发现；本入口没有工具注册、setActiveTools、资源发现拦截、trust 自动批准或 UI 调用。
