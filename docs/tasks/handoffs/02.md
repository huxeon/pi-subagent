## 实际接口与用法

```ts
import { createRpcAdapter, createRpcAdapterFactory } from "./rpc-client.ts";

const client = createRpcAdapter(resolvedChildConfig);
await client.start(); // SDK.start() + SDK.getState()，失败会尝试 stop()
const unsubscribe = client.onEvent(listener); // 必须先于 prompt 安装
const initialDisposition = await client.prompt(message);
const nextDisposition = await client.prompt(nextMessage, undefined, mode);
const text = await client.getLastAssistantText();
unsubscribe();
await client.stop();
```

- `createRpcAdapter: RpcAdapterFactory` 是生产工厂；默认构造器固定为官方 `new RpcClient(options)`。导入模块或构造适配器不会启动进程。
- `createRpcAdapterFactory(createClient?: RpcClientCreator): RpcAdapterFactory` 提供最小构造注入；creator 接收完整 RpcClientOptions，返回与现有 RpcAdapter 相同的 SDK 方法集合。没有自制 JSONL 协议或私有 SDK 进程字段访问。
- `start()` 只有在 SDK.start 和一次 getState 都成功后才完成。getState 使用官方 30 秒请求期限；不会提前提交 prompt。启动/握手失败会等待停止并重新抛出原错误。清理也失败时不覆盖启动错误，后续 `stop()` 仍可观察清理失败。
- 适配器是**单次生命周期**：每个子进程创建一个新适配器；重复 start、stop 后 start 均拒绝。不做恢复或重新启动。
- `getState()` 保持 SDK 状态对象及错误；不增加模型查询、选择修正或 thinking clamp。
- `prompt(...args)` 原样委托，包括参数个数、images、mode，以及 started/queued/handled。初始和后续调用形式由管理器按上例选择；适配层不猜测空闲/运行状态，不转换 steer/followUp，不调用 promptAndWait。
- prompt 拒绝直接失败，包括压缩期间拒绝；不等待、不排队补偿、不重试。这里不改变 Pi 默认的模型运行重试配置。
- `onEvent()` 原样传递监听器和取消订阅函数；异步回调捕错仍由后续管理器/回报层负责。

### Pi 1.5.0 文本缺失值兼容

首轮真实 CLI 探针发现：空会话的 `getLastAssistantText()` **实际返回 undefined**，不符合官方 RPC 文档及 RpcClient 的 `Promise<string | null>` 声明。

原因：AgentSession 在没有 assistant 消息时返回 undefined，RPC handler 直接写 `{ text }`，序列化后字段缺失，RpcClient 读取缺失字段得到 undefined。

适配层使用 `(await client.getLastAssistantText()) ?? null`，落实现有规格的 `string | null` 约定：

- string（包括空字符串）原样保留；null 保留；SDK 运行时 undefined 转为 null。
- 不增加请求或重试，不吞掉取结果错误。
- 默认 fake 测试和真实 CLI 空会话探针都已验证此边界。
- 未修改规格或 node_modules。任务 04 可以直接按 null 表示“没有可用 assistant 文本”。

## CLI 定位与启动参数

`resolvePiCliPath()`：

1. 使用**同一 SDK 公开导出的 `getPackageDir()`** 获取加载中的 Pi 包目录，适用于宿主别名/虚拟模块，而不是从扩展的 cwd、argv[1] 或 PATH 推断。
2. 目录必须是绝对路径；遵循官方 `PI_PACKAGE_DIR` 覆盖机制，但拒绝相对目录。
3. 读取该目录的 package.json，要求包名为 `@earendil-works/pi-coding-agent`、版本等于加载中的 `VERSION`；缺失/错误元数据立即失败，不回退到其他安装。
4. 读取 `bin.pi`，resolve + realpath 得到绝对路径，并验证是可读普通文件。SDK 使用 `node <cliPath>`，因此不要求可执行位。

## 停止边界

- 所有并发/重复 `stop()` 返回同一个 Promise，仅调用官方 SDK.stop 一次，避免 SDK 自身多次 stop 的进程字段竞态。
- stop 若遇到正在执行的 SDK.start，只等待它的 100ms 启动检查，不等待 getState 就绪请求。
- 强制终止依赖已核对并实际测试的 **Pi 1.5.0 官方 stop**：SIGTERM，等待 exit，1000ms 超时后发送 SIGKILL 并完成。已退出但保留 SDK 进程对象时，同样约 1 秒内完成；未启动客户端直接完成。
- 不额外实现进程管理器，也不使用一个只结束 Promise、无法真正杀进程的外层计时器。此边界依赖官方 SDK 的有界实现；注入的测试 client 应遵守同一约定，不保证任意永不 resolve 的自定义 stop 有界。
- SDK 的超时兜底是在发送 SIGKILL 后完成，并不额外等待操作系统 exit 回调；测试另外确认直接子进程最终消失。没有进程树清理保证。
- start/stop 的基础重叠已测试，但名字预留、全体并行停止、运行时替换与延迟回报保护仍属于任务 03/04。
- 特别注意：stop 不等待尚未完成的 getState；被打断的 start 何时 reject 仍受 SDK 请求/退出处理影响（请求自身期限 30 秒）。后续生命周期不能把“等待所有启动结果”当作停止子进程的前提。

## 可复用测试设施

`tests/helpers/fake-rpc-client.ts` 的 `FakeRpcClient implements RpcAdapter` 可直接供管理器注入：

- `calls` 记录 method 和原始 args。
- `state`、`disposition`、`text` 可设定；默认无模型调用。
- `listeners`、`emit(event)` 可控制同步事件流，检查取消订阅。
- 可用 Node 的 `t.mock.method(fake, method, implementation)` 注入拒绝或 deferred Promise，以测试启动中、提交中、关闭竞态。现有 rpc-client 测试有示例。
- fake 不模拟 RPC 协议或自动执行 agent；后续需显式 emit settled，不应把 prompt 接收当作完成。

停止测试的 `.mjs` fixture 只是定时器和受控退出/忽略 SIGTERM 的进程，**不实现 RPC**。仅 getState 被 stub，其余启动、信号、exit 和强杀完全使用官方 RpcClient。
